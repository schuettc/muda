## Stage 2: the full loop on two unseen repositories

Two Go repositories, each with a CI pipeline restructured days before measurement. Each ran measure → diagnose → fix → verify, with every checkpoint approved by a human.

| | Repository A | Repository B |
|---|---|---|
| Baseline | 19 CI runs (window started after the restructure; low confidence) | 17 CI runs (same) |
| Main finding | A cache that never warms (R11), measured | The same waste, suspected; approved as an experiment |
| Fix | One line: the light job stops saving the shared cache | Two lines, same idea, for two light jobs |
| Verified on the real pipeline | go-ci step ~110s → ~22s on a same-commit re-run; realistic saving ~50–75s per run | Total CI ~289s → ~104s on a new commit; experiment criteria met |
| Gate inventory | Unchanged | Unchanged |

**What stage 2 taught muda, all shipped before release:**
- **R11, "A cache that never warms".** Both repositories had parallel jobs racing to save one cache key: a light job saved a near-empty entry first, and every later run hit it and rebuilt everything. No recipe covered it, and diagnose correctly refused to file it under one that didn't fit.
- **Unchanged workflow files verify automatically.** The first fix needed exemptions for three workflow files, two of them byte-identical, each listed twice. After the change, the second fix needed one exemption, for the one changed file, reviewed against an exact diff.
- **A Go stack**, with Go-specific guidance in four recipes (toolchain pinning, the test-result cache, host-independent builds, setup-go's default-on cache).
- **Pipeline changes inside the window** are reported by `measure`, with runs before and after; numbers carry confidence labels instead of blocking on sample size.
- **Suspected findings can be approved only as labelled experiments**, record PRs learn a repository's PR conventions, and a fix whose PR never merged can be reopened.

## Stage 3: a public repository, read-only

One open-source Python project with a cross-platform test matrix, measured over 30 days (about 230 test runs) and diagnosed without any change to the project.

| Finding | Label | Evidence |
|---|---|---|
| Windows test step about 2.4× slower than Linux for the same tests and workers | suspected | Six job logs compared; names the paired run with per-test durations that would settle the cause |
| One matrix Python version resolves to different patch releases per OS | measured | Five named jobs; framed as consistency, not time |
| Two deprecation warnings in a maintenance workflow (an input, and an action's runtime) | measured, two findings | Warning annotations with counts |

A person reviewed every finding and agreed each is real and correctly evidenced. No false positives. The session also held back where evidence didn't support a claim: the cache recipe "not shown" (full entries restored), re-verification "does not apply" (nothing deploys after CI), and an unusual action reference checked and found correct rather than reported.

**Known limit:** annotations are read one check run at a time, so on a repository with about 10,000 check runs in the window, notices covered only the first nine days. The session said so rather than treating the gap as no notices.
