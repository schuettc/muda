## Symptom

Every image build reinstalls and re-exports its dependencies although no
third-party dependency changed. The image copies its dependencies and its own
code as one layer, or the dependency step reads a file that changes on every
release (the package's version, or exact pins on the repository's own
packages), so a code change or a version bump invalidates the whole stack.

## Detect

```sh
muda measure
muda logs 12345 --job 67890 --grep "(?i)CACHED|exporting layers|DONE [0-9.]+s"
```

Run ID 12345 and job ID 67890 are illustrative; substitute consecutive measured
deploys that built the same image. Split each image build into install, export
layers, export cache and publish, using BuildKit's per-step `DONE` times. Then,
for each deploy where the dependency step ran rather than showing `CACHED`,
diff the file that step copies against the previous deploy: if only the
package's own version line or the pins on the repository's own packages
changed, this is the waste. Check the final stage too: copying one virtual
environment that holds both the dependencies and the package re-exports
gigabytes on every code change.

## Fix

Give third-party dependencies their own layer, keyed on a file that lists only
them, and keep the repository's own packages and the code in later, smaller
layers. Equal third-party dependencies then give an equal cache key, whatever
else changed. Approve one scoped finding and change per PR.

## Stacks

### docker

Before: one stage installs dependencies and the package into a virtual
environment, and the runtime stage copies that environment as one layer.
After: the dependency layer is copied from a stage that holds only the
third-party list; the repository's own wheels are a second layer and the
package a third (for example a package stage FROM the same base, installing
with `--no-deps`). BuildKit keys `COPY` on content and `FROM` on the resolved
digest, so an unchanged list and base reuse the layer.

### python

Before: the dependency step copies `pyproject.toml` (whose version changes on
every release) or a lock that pins the repository's own packages exactly.
After: an early stage exports the third-party requirements from the lock,
with exact versions and the repository's own packages removed, and the
dependency step copies only that file and installs it with `uv pip install`
(pip is slower for the same list). The real version and the repository's own
packages are installed afterwards with `--no-deps`. Keep the exact pins for
reproducibility; only the layer key stops depending on them.

## Traps

- `CACHED` followed by tens of seconds is not a miss: BuildKit is downloading
  the cached layer for a later step. Splitting the layers removes that
  download too.
- The normalized file may differ from the real one only in its version and its
  pins on the repository's own packages; any other edit hides a real
  third-party dependency change.
- Re-tagging the base to the digest already pulled does not invalidate the
  cache, because `FROM` is keyed on the digest. A change of digest does.
- Key the layer on a lock export, never on a resolve done during the build.
  Resolving the manifest's version ranges against the package index on every
  build changes the key whenever any loosely pinned dependency publishes a
  release, so the cache holds only between upstream releases.
- Print the hash of the file the layer is keyed on in the build log, so a miss
  shows which input changed.
- The first deploy after the change rebuilds everything (the layer identity
  changes); judge the fix on later deploys with the right kind of change: one
  that touches only code or the repository's own packages.

## Verify

```sh
muda compare --before 2026-09-01..2026-09-08 --after 2026-09-08..2026-09-15 --gates
muda record check
```

The dates above are example windows; replace them with representative
before/after windows. On deploys whose third-party list is unchanged, the
dependency layer and its export show `CACHED` and only the small layers
rebuild. Confirm the installed packages are unchanged. Verify on the real PR
pipeline and again after merge. The gate inventory must remain the same or
stronger; the user confirms the receipt.

## Evidence

From one adopter's deploys on a 4-CPU, 16 GB runner: with dependencies, the
repository's own packages and the code in separate layers, three image builds
went from 8.1 minutes to 75 seconds on a deploy that changed only code and the
repository's own pins, and took 68 to 80 seconds on a second deploy that
re-tagged the base to the same digest; in both, the dependency layer and its
export were `CACHED`. One earlier miss turned out to be a fresh resolve
picking up an upstream release, which the printed key hash showed. When the
third-party list did change, `uv pip install` reinstalled the layer in 45 to
87 seconds per image across 3 deploys, against 78 to 122 seconds with pip;
exporting the layer still took 75 to 95 seconds. Record actual before/after measurements and their
run/job/step sources in the finding receipt; never substitute these numbers.
