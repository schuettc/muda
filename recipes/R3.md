## Symptom

An image rebuilds every deploy although source and locked dependencies did not
change; a temporary credential changes its asset identity.

## Detect

```sh
muda measure
muda logs 12345
muda logs 12345 --job 67890 --grep "(?i)build|push|skip|exist|found|cached|publish"
```

Run ID 12345 and job ID 67890 are illustrative; substitute each measured deploy
run and every relevant job, including separate image-build jobs. Missing logs
are unavailable evidence, not zero work. An empty grep is not evidence of no
work; widen the pattern. Then:

1. From each deploy's build and skip lines, list each image asset it built,
   pushed or skipped.
2. Find consecutive deploys whose merged diff did not touch that image's build
   inputs: read `git diff <a> <b> -- <image context> <Dockerfile> <IaC file
   that defines the asset>` for the two deployed commits. In the IaC file,
   only edits to that asset's construction or inputs count (its context,
   Dockerfile, build arguments or definition); edits elsewhere in it do not.
   If the image still rebuilt, W1 is measured for that asset.
3. Read the IaC's image-asset construction for hash inputs whose values change
   between runs: build arguments or other inputs fed from environment
   variables, tokens, credentials, timestamps or run IDs. A rotating value
   there explains step 2; without step 2 it is only suspected. A rebuild from
   step 2 with no rotating input found is still measured W1, but R3 is not
   confirmed: check the other listed recipes or report it as unmatched.

This is log/code diagnosis, not a stack-specific CLI signal.

## Fix

Remove credential values from content identity and pass authentication through
secret mounts only where needed. Add asset-hash and leakage tests for every
related asset, rather than copying a comment. Agree the change and ship a PR.

## Stacks

### cdk

Before: a token in `DockerImageAsset` build arguments changes the hash.
After: use the framework/build secret facility and test that token rotation
does not change identity. A temporary `invalidation: { buildArgs: false }`
needs proof that meaningful non-secret arguments remain represented; prefer
R6’s separate image build rather than broadly disabling invalidation.

### docker

Before: `ARG INDEX_TOKEN` followed by an install. After: a BuildKit secret
mount on only the authenticated `RUN`, for example
`RUN --mount=type=secret,id=index_token,env=INDEX_TOKEN ...`.
Enable compatible Dockerfile syntax; never persist the token in a layer.

## Traps

- Copy drift beats comments (lesson 3): test sibling assets as well as the one
  initially fixed.
- Disabling all build-argument invalidation can hide real input changes; secret
  transport is not permission to omit meaningful inputs from identity.
- Token values must not appear in history, exported layers, logs or receipts.
- A skipped build can mean an existing artifact, not a layer-cache hit. Correlate
  hash, build/push/skip result and layer evidence by asset.

## Verify

```sh
muda compare --before 2026-09-01..2026-09-08 --after 2026-09-08..2026-09-15 --gates
muda record check
```

The dates above are example windows; replace them with representative before/after windows.
Repeat unchanged inputs with rotated credentials: identity stays stable, while
real source/dependency changes still invalidate it. Inspect image-build jobs and
artifact history without exposing secrets; require complete per-asset outcomes.
Verify on the real PR pipeline and again after merge. The gate inventory must
remain the same or stronger; the user confirms the receipt.

## Evidence

Illustrative example only, not a measured adopter result: an asset built in 5 of 5 unchanged deploys before the fix; subsequent
unchanged deploys reuse its existing identity without rebuilding.
Record actual before/after measurements, coverage, tree/asset identities and
run/job/step sources in the finding receipt; never substitute these example numbers.
