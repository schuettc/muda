## Symptom

A deploy step that updates a container service takes minutes, although the
image is already built and pushed. Most of the time is the infrastructure tool
waiting for the service to settle after a new task definition: a new task
starts and passes health checks, the old one drains and stops, and the tool
notices. A dependent stack may also wait for all of this before it starts.

## Detect

```sh
muda measure
muda logs 12345 --job 67890 --grep "(?i)UPDATE_IN_PROGRESS|UPDATE_COMPLETE|steady state"
```

Run ID 12345 and job ID 67890 are illustrative; substitute the measured deploy
job. muda reads no cloud provider, so ask the user for read-only output from
the provider for the same deploy: the stack's events, the service's events and
its tasks' pull, start and stop times, and the target group's health-check and
deregistration settings. Then split the rollout, per service on the deploy's
critical path, into phases: stack update to task start, schedule, image pull,
container start, healthy, old task deregistered, drained, stopped, service
settled, and the tool noticing. Flag a phase that is long next to the work it
waits for: a health-check interval far longer than the check takes, an old
task killed at its stop timeout instead of exiting, or an image build that
starts only after an unrelated stack finishes.

## Fix

Fix the longest phase first, then split the rollout again: fixing one phase
moves the bottleneck to the next, so judge each fix by the rollout total, not
by its own phase.

1. Build and publish a service's image while its stack waits on other stacks;
   only the stack deploy needs to wait.
2. Make the old task exit promptly on SIGTERM, releasing any in-flight work,
   so it stops in seconds instead of at its stop timeout.
3. Shorten a health-check interval that is long next to the check's cost.
4. Shorten the deregistration delay only where no response lives longer than
   the new delay.

Approve one scoped finding and change per PR.

## Stacks

### cdk

Before: the dependent stack's image asset is built inside its own deploy, after
the stacks it reads from have finished; the container has no SIGTERM handler,
so the old task runs until `stopTimeout`; the container health check runs every
60 seconds. After: an earlier, parallel workflow step builds and publishes the
dependent stack's asset (`cdk deploy` then finds it already published), the
container handles SIGTERM, and the health-check interval matches the check's
cost. Keep the target group's deregistration delay unless no connection or
streamed response outlives the shorter value.

## Traps

- A faster phase does not shorten the rollout by itself. In one deploy the
  health check passed in 22 seconds instead of 85 and the rollout total did not
  move: the time shifted to the old task's kill, the service settling and the
  tool's lag.
- The tool's own polling lag (around 30 to 60 seconds) cannot be tuned.
- With a desired count of 1, a minimum healthy percent below 100 still waits
  for the new task to be healthy.
- A prebuilt asset must have exactly the hash the later deploy computes,
  including every input that feeds the image hash; a failed background build
  must fail the deploy visibly.
- Long-lived responses (streaming, subscriptions, large downloads) are cut when
  the deregistration delay runs out. Check for them before lowering it.
- A SIGTERM handler that drops in-flight work trades rollout time for lost jobs.
- Only services on the deploy's critical path matter; speeding up one that runs
  in the background saves nothing.

## Verify

```sh
muda compare --before 2026-09-01..2026-09-08 --after 2026-09-08..2026-09-15 --gates
muda record check
```

The dates above are example windows; replace them with representative
before/after windows. Split the rollout into phases again on the post-merge
deploys and compare the rollout total and the deploy's critical path, not one
phase. Confirm the old task exits 0 when it stops, and that no long-lived
connection ended at the drain limit. Verify on the real PR pipeline and again
after merge. The gate inventory must remain the same or stronger; the user
confirms the receipt.

## Evidence

From one adopter's deploys on a 4-CPU runner: building a dependent service's
image while its stack waited cut that deploy step from 392 seconds to 207 to
264 seconds across 6 deploys; a SIGTERM handler made the old task stop in 12
seconds instead of being killed at 42, and that service's rollout went from
3m24s to 2m44s (1 deploy); shortening the health-check interval alone did not
change the rollout total. Record actual before/after measurements and their
run/job/step sources in the finding receipt; never substitute these numbers.
