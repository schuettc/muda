## Symptom

A producer publishes, but a consumer update fails, is cancelled or remains
unmerged without a visible explanation.

## Detect

```sh
muda measure
muda logs 12345
```

Replace illustrative run ID 12345 with each failed chain run. Classify the actual
error line, not an echoed script. Separate merge races, contract breaks, unrelated
CI failures and transients. An intentional operator approval wait is not an
automated stall; record the expected hand-off and approval policy first.
Whenever a required check is added to a branch, audit every workflow that runs
`gh pr merge` against it: a merge issued seconds after opening the PR is now
rejected by the ruleset. For each cloud role trusted through OIDC, list the
workflow_run, schedule and repository_dispatch workflows that assume it and
compare the trusted subject with the repository's default branch.

## Fix

With user approval of the automation policy, arm native auto-merge on trustworthy
gates rather than timing a merge after polling. Use per-package concurrency,
fresh-base rebuilds with bounded retries, superseded-PR cleanup and one visible
issue per failed package. Preserve manual approvals; deliver the change as a PR.
Any automated merge arms auto-merge pinned to the gated commit, then polls until
the PR is MERGED. It fails fast on a failed or cancelled required check or a
closed PR, and fails loudly on timeout.

## Stacks

### github-actions

Before: poll checks then merge on a timer under one shared concurrency group.
After: request native auto-merge after opening the PR, use a status-readable
token, isolate concurrency per package and re-arm after a bounded fresh-base
rebuild. Alert on every non-merge failure or cancellation, and close the issue
on later success. Write retry-budget arithmetic inside the job timeout.
Arm with `gh pr merge --auto --merge --match-head-commit <gated sha>`; never add
`--delete-branch` when the head is a long-lived branch. Derive an OIDC trust
subject per repository from `gh api repos/OWNER/REPO --jq .default_branch`.

## Traps

- A successful check may not yet have propagated into merge eligibility; native
  auto-merge avoids a timed race without bypassing required checks.
- An installation token may lack status-rollup read access. Prove permissions
  with the real caller and do not treat unreadable status as green.
- One concurrency group keeps only one pending run; a newer pending run can
  replace another package’s update. Isolate work items.
- `failure()` alone misses cancellation; a timeout must produce a visible outcome.
- Diagnose from evidence, then correct earlier claims openly (lesson 6).
- A merge queue may need plan/visibility support. Probe availability before
  relying on its tested-tree guarantee; preserve review and environment gates.
- workflow_run, schedule and repository_dispatch runs execute on the default
  branch, so their OIDC subject names it, not necessarily `main` (unless the job
  uses an `environment:` or the repository a custom subject template). A wrong
  subject can stay latent while a broader role masks it; test the exact trust
  set.
- Tightening a ruleset breaks automation that merged immediately and passed
  before. Treat a new required check as a change to every merging workflow.
- An operator wait is not automated failure. Alert against the agreed automatic
  hand-off deadline, not time the user intentionally spends reviewing.

## Verify

```sh
muda compare --before 2026-09-01..2026-09-08 --after 2026-09-08..2026-09-15 --gates
muda record check
```

The dates above are example windows; replace them with representative before/after windows.
Observe successful, dirty-branch, failed-check, timeout and cancellation paths,
and one real run of each default-branch trigger that assumes a role. Each
automatic non-merge ending has a visible package-specific outcome; later success
resolves it. Compare automated failure/retry rates separately from operator wait
time.
Verify on the real PR pipeline and again after merge. The gate inventory must
remain the same or stronger; the user confirms the receipt.

## Evidence

Illustrative example only, not a measured adopter result: 4 silent failures in 12 automated hand-offs become 0 silent failures;
remaining failures have issues and intentional review waits are reported separately.
Record actual before/after measurements, coverage, tree/asset identities and
run/job/step sources in the finding receipt; never substitute these example numbers.
