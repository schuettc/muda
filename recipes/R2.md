## Symptom

An unchanged deploy updates every stack; the differences are framework metadata
rather than application resources.

## Detect

```sh
muda measure
muda logs 12345
muda logs 12345 --job 67890 --grep "(?i)update|no changes|deploy|version"
```

Run ID 12345 and job ID 67890 are illustrative; substitute each measured deploy
run and every relevant job, including separate image-build jobs. Missing logs
are unavailable evidence, not zero work. An empty grep is not evidence of no
work; widen the pattern. Then:

1. From each deploy's log lines, count updated and unchanged stacks. Separate
   the deploys where all or most stacks updated from those where few did. If
   every deploy updated every stack, compare consecutive deploys instead.
2. Compare a runtime or tool version string (framework, Node, CLI) between the
   two groups or pairs, using the deploy logs and the synthesized metadata;
   decode metadata when necessary.
3. Read the merged diff between those deploys, then the template difference
   (deployed versus synthesized) or change set for each updated stack.
   All-stacks updates with no application change, together with a version
   change, mean W1 is measured only when that difference contains only the
   framework metadata resource. Correlation alone is suspected. A version
   change without that update pattern is only suspected.

The cloud side settles a suspected finding: the deployed template or change
set for each updated stack. When the deploy logs do not show it, ask the human
to run the provider's read-only get-template or describe-change-set command and
paste the output. Without that output, the finding stays suspected. muda itself
reads no cloud provider and holds no cloud credentials.

The agent correlates runtime-version stamps with updates; muda does not parse
framework output or infer W1 from a slow step alone.

## Fix

Disable nonfunctional version reporting and add a fail-closed synthesis guard.
Retain meaningful resource changes and required deploy gates. Obtain user
approval, then deliver the change as a PR.

## Stacks

### cdk

Before: `versionReporting: true` in framework configuration. After:
`versionReporting: false` (or `"versionReporting": false` in `cdk.json`).
Synthesize the real app and assert no `AWS::CDK::Metadata` resource is emitted.

### github-actions

Before: template inspection silently succeeds with an empty file glob. After:
collect the synthesized templates explicitly, fail if none exist, and fail on
read/search errors as well as on forbidden metadata. Keep this job required.

## Traps

- The first deploy removes metadata and legitimately updates stacks. Only a
  second unchanged deploy proves no-op behavior.
- An empty glob and `|| true` can make a grep gate pass without inspecting a
  template. Missing data and tool errors must fail, not look like zero matches.
- Measure before optimizing: a version string can explain an apparently slow
  deploy better than stack parallelism (lesson 1).
- Exemptions name stable workflow/job/check identities, never a step index;
  stale or ambiguous identities must fail loudly.

## Verify

```sh
muda compare --before 2026-09-01..2026-09-08 --after 2026-09-08..2026-09-15 --gates
muda record check
```

The dates above are example windows; replace them with representative before/after windows.
Observe the first removal deploy and then a same-tree repeat with complete
per-stack evidence: zero unintended updates and zero unintended image builds.
Missing image-job logs cannot establish a no-op.
Verify on the real PR pipeline and again after merge. The gate inventory must
remain the same or stronger; the user confirms the receipt.

## Evidence

Illustrative example only, not a measured adopter result: 8 of 8 unchanged stacks updated before the fix; 0 of 8 update on the
second unchanged deploy, after the one-time metadata removal.
Record actual before/after measurements, coverage, tree/asset identities and
run/job/step sources in the finding receipt; never substitute these example numbers.
