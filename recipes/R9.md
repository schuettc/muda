## Symptom

A platform change breaks CI after warnings repeated unnoticed for days, or a
warning hides a gate that never actually ran.

## Detect

```sh
muda notices
muda scan
muda logs 12345
```

Replace example 12345 with a notice’s source run. Group by normalized signature,
read example annotations and real log context, and distinguish deprecation from
verification bypass. Missing annotation coverage is unavailable, not zero notices.

## Fix

Assign an owner and deadline per signature; review the producer’s supported
upgrade and breaking changes, pin the fix and run the real consumer. Make
verification errors fail loudly. Obtain user approval and deliver one scoped
remediation per PR; only resolve notices after complete evidence.

## Stacks

### github-actions

Before: ignored action-runtime deprecations, obsolete inputs and “trusting”
warnings. After: upgrade the producing action at its source first, then move
consumer pins after its release; align inputs with the pinned release’s
contract. Use reviewed full references where major tags are absent and keep
non-secret identifiers in repository configuration.

### node

Before: changing the workflow’s Node setup is assumed to fix a shared action’s
obsolete embedded runtime. After: inspect the action manifest and update/test
the producer’s declared runtime, dependencies and emitted artifact first.
Then bump the caller’s pin and verify real executions no longer emit the notice.

## Traps

- A warning that says “trusting” or “skipping” a required check is a defect,
  not harmless noise. CI green does not prove that check ran (lesson 4).
- Fix obsolete runtimes in shared actions producer-first; caller interpreter
  setup cannot change an action’s embedded runtime.
- Read breaking notes and the pinned action’s actual input contract before
  changing the caller. A new input on an old pin may fail or be ignored.
- A partial scan cannot prove a signature disappeared. Do not close an issue
  from missing data, and do not invent a scheduled muda watcher command.
- Exemptions must refer to stable semantic check IDs and expire; fail loudly
  on stale IDs rather than letting a shifted step index exempt another gate.

## Verify

```sh
muda compare --before 2026-09-01..2026-09-08 --after 2026-09-08..2026-09-15 --gates
muda record check
```

The dates above are example windows; replace them with representative before/after windows.
Compare notice groups with complete coverage and inspect their source logs.
Resolved signatures no longer appear; previously bypassed checks now execute
and fail on errors. Preserve all status and deployment protections.
Verify on the real PR pipeline and again after merge. The gate inventory must
remain the same or stronger; the user confirms the receipt.

## Evidence

Illustrative example only, not a measured adopter result: 3 warning signatures become 0 on a complete after window, and 1
previously bypassed verification is now an executed, required check.
Record actual before/after measurements, coverage, tree/asset identities and
run/job/step sources in the finding receipt; never substitute these example numbers.
