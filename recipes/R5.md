## Symptom

A slow serial test suite or multi-stack deploy appears to need more workers,
but repeated computation or undeclared dependencies may be the real constraint.

## Detect

```sh
muda measure
muda scan
muda logs 12345 --grep 'slowest|durations'
```

Run ID 12345 is illustrative; substitute the measured test run.
Rank slow steps and inspect independent-job candidates. Profile each test in the
reference environment before adding workers: rank the slowest tests and look for
one helper called with the same arguments by several tests. Inspect the actual
synthesized stack dependency graph.
A static serial-job signal is a hypothesis, not proof of safe parallelism.

## Fix

Remove duplicate computation first using read-only shared results with parity
assertions, and cap native thread pools before native libraries load so they do
not oversubscribe cores on tiny inputs. Then introduce a fixed, bounded worker
count or deploy concurrency, only after proving dependencies. Approve one scoped
finding and change per PR.

## Stacks

### python

Before: three tests recompute the same expensive result. After: a
module-scoped read-only fixture supplies byte-identical results, then a fixed
worker count runs the suite. Compare serial, load-balanced, scope-balanced and
three repeated bounded-worker runs with identical pass counts and no skips.
Set `OMP_NUM_THREADS=1` in the test job's environment or at the top of the root
conftest, before OpenMP-backed libraries are imported; the runtime reads it once.
Serve a repeated sweep from a session-scoped cache and put its tests in one
`xdist_group` under `--dist loadgroup`, so one worker computes it once; xdist
workers never share a session. Point fixed cache roots at each test's temp
directory with a fixture.

### github-actions

Before: unrelated jobs are connected by `needs` merely to serialize them.
After: remove only disproven edges and size workers to actual runner resources.
Keep genuine gate and artifact dependencies, required check identities and
no-rerun/no-skip parity checks.

### cdk

Before: all stacks deploy serially or rely on a handwritten edge list.
After: use one real app builder for entry point and tests, derive parameter
producer/consumer dependencies from synthesized templates for every stage,
require declared ancestors and explicit external-parameter allowances, then
enable bounded concurrency capped to the graph’s width.

### go

Before: a re-run, a commit that does not touch a package, or a new runner that
restores GOCACHE makes the suite look fast, because `go test ./...` replays the
test-result cache for unchanged packages and prints `(cached)` instead of
running them. A new runner is not a fresh run when GOCACHE is restored. After:
measure fresh runs only. Only `-count=1` or an empty GOCACHE guarantees a fresh
run (`go clean -testcache` empties the test results); a change to the test
binary, to cacheable flags, or to environment variables or files a test reads
invalidates a cached result. `-race` costs CPU and memory, often several times
more, so time race and non-race runs separately. Before reaching for sharding,
use what the toolchain has: `-p` defaults to GOMAXPROCS and sets how many
packages build and test at once, and `-parallel` applies only to tests that call
`t.Parallel()` inside a package.
A warm build cache from a cache fix turns this cache on in CI; see R11.

## Traps

- The model of where time goes is wrong until measured (lesson 1): duplicated
  computation can dominate more than serial execution.
- `auto` workers can exhaust memory on small runners. Use a fixed count and
  observe resource limits, not just duration.
- Native thread pools can use every core per test on tiny inputs; more workers
  multiply that contention.
- Parallel runs expose shared host state. Plain parallel can pass while another
  distribution mode fails, because caches hard-coded under a fixed temp root
  race across workers.
- Challenge a "the gate needs serial runs" exemption with the standard's
  named-test and revert rule.
- Native dependencies may require a target-architecture container with an exact
  base, frozen lock and credentials in environment/secret mounts only.
- Deploy mirrors may run on smaller runners and take longer than reference CI.
- Estimates err in both directions (lesson 5). Keep guesses out of PR titles;
  receipts contain measured deltas.
- Tests that recreate app wiring do not prove the real entry point’s graph. An
  explicit test-only build-output override must not make production synth
  tolerate missing inputs.

## Verify

```sh
muda compare --before 2026-09-01..2026-09-08 --after 2026-09-08..2026-09-15 --gates
muda record check
```

The dates above are example windows; replace them with representative before/after windows.
Compare critical-path improvement and exact check/pass counts, without reruns
or skipped tests. Observe repeated bounded runs and every stage’s dependency
guard; never trade race safety or coverage for a shorter wall clock.
Run the suite at least 3× under the final distribution mode, and search the
source for literal temp roots with no environment override. Measure peak memory
under the runner's real CPU and memory limits before claiming a worker count.
Verify on the real PR pipeline and again after merge. The gate inventory must
remain the same or stronger; the user confirms the receipt.

## Evidence

Illustrative example only, not a measured adopter result: a 480-second test step becomes 150 seconds after eliminating duplicate
computation and adding bounded workers with equal pass counts; capping native
threads alone might take it from 480 to 300 seconds.
Record actual before/after measurements, coverage, tree/asset identities and
run/job/step sources in the finding receipt; never substitute these example numbers.
