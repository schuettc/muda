---
id: R11
title: A cache that never warms
waste: [W4]
signals: [slow-step]
stacks: [github-actions, python, go]
---

## Symptom

A setup or build step stays slow on every run although its dependency cache
reports a hit. The dependency download and compile repeat until the lockfile
changes, and the same thing can happen again after the next change.

## Detect

```sh
muda measure
muda logs 12345 --job 67890 --grep "(?i)cache|restore|reserve|saving"
```

Run ID 12345 and job ID 67890 are illustrative; substitute consecutive measured
runs on the same cache key and every job that restores or saves that key.
Missing logs are unavailable evidence, not a warm cache. An empty grep is not
evidence of a hit; widen the pattern. Then:

1. Across consecutive runs on the same key, compare the restored cache size
   and the hit lines. Judge "near-empty" against the size of the entry the full
   job saves, not by an absolute number: a hit that restores a small fraction
   of that while the step then downloads or compiles the full dependency set
   points at a near-empty entry.
2. Find the run that created the key. In its jobs, look for the save that won
   and for the refused saves ("Unable to reserve cache ... another job may be
   creating this cache") or other failed saves. Later runs show "not saving
   cache" or "cache hit occurred on the primary key", so no job repairs it.
3. Compare the step time on a warm entry (an earlier key, or a run after the
   entry was repopulated) against a run that hit the near-empty entry, with
   identical work: the same lockfile, the same commands and the same runner
   type.
4. The repository's cache list on the platform shows each entry's key and
   size. Read the size of the entry under the key in question, and note it as
   evidence, not as a fix.

R11 is measured only when a near-empty entry is being hit and identical work
is slower on it than on a warm entry. Otherwise it is suspected: a hit line
alone, or a slow step alone, does not settle it.

## Fix

Only the job that produces the full dependency set saves the shared key. In
jobs that build or download nothing, turn caching off or make it restore-only,
so they can still read the entry but never write it. A setup action's built-in
cache can be on by default: a job with no cache input may still save the key,
so turn it off explicitly. Alternatively give each
job its own key, so a light job's save cannot claim a heavy job's entry. An entry cannot be overwritten under
its key, only deleted. Delete the poisoned entry and let the next full run
repopulate it. Never drop
or rename a required check or job to win the race. Obtain user approval and
deliver one scoped change per PR.

## Stacks

### github-actions

Before: several parallel jobs use `actions/cache`, or a `setup-*` action's
built-in cache, with the same lockfile-hash key; whichever job finishes first
after a key change saves it. After: the job that installs or builds the full
dependency set is the only writer, using `actions/cache` or its save step;
other jobs use the restore-only form of the cache action or turn the setup
action's built-in cache off. Read the pinned action's own inputs before changing
them; a built-in cache may offer no restore-only mode, so turning it off in a
light job is the general answer there. Remove the near-empty entry through the
platform's cache management, then let one full run save it.

### python

Before: a lint or tool job installs one small tool with the same setup action
cache as the test job, and the cache key is derived from the requirements or
lock file, not from what the job installed. The light job's small package cache
wins the key, so the test job hits it and downloads and builds everything else.
After: only the job that installs the full requirements enables the built-in
cache or saves the key; the tool job turns caching off or uses its own key.
The built-in cache holds the package manager's download and wheel cache, not
the installed environment, so a warm hit still runs the install, only without
downloads or builds; compare against that, not against zero. Check whether
native packages are built from source on a miss, since that is where most of
the repeated time goes.

### go

Before: `actions/setup-go` has its built-in cache on by default (since v4). The
key comes from the dependency file's hash (`go.sum` in older majors, `go.mod`
from v6.3.0; `cache-dependency-path` overrides it) and also includes the runner
OS, arch and Go version, so only jobs on the same OS, arch and Go version share
an entry. The entry holds both the module cache and the build cache. A lint or
tool job with no `cache:` input still saves that key, so whichever such job
finishes first owns it. After: only the job that builds and tests the full
module keeps the built-in cache; set `cache: false` in jobs that build little.
Build cache entries are keyed by GOOS/GOARCH, build tags and flags such as
`-race`, so a light job's entry can be large and still useless to the heavy job:
compare what was built, not only the size. After a hit, `go build -x` in the
heavy job prints a compile command for every package it still rebuilds; compare
its step time with a warm run. A warm build cache also enables Go's test-result
cache: `go test` replays `(cached)` results for unchanged packages instead of
running them. Keep `-count=1` (for example `GOFLAGS: -count=1` on the test
step), or the required gate stops running every test. Pass criteria for the
fix include: the gate still runs every test (0 `(cached)`).

## Traps

- A hit is not a warm cache. Read the restored size and the step's own work
  before calling a cache healthy; a configured cache is not proof either.
- Deleting the entry alone does not fix it. The race recurs on the next key
  change unless only the full job can save the key.
- Per-job keys multiply stored entries. Say so explicitly, estimate the total
  against the platform's repository cache storage limit, and expect eviction of
  older entries when the limit is passed, which brings back cold restores.
- Do not "fix" the race by removing a job from parallel execution or dropping
  it from required checks; the gate inventory must not shrink.
- A refused save in one run is normal when jobs share a key; it is only waste
  when the winning save was near-empty.
- Entries are scoped by branch: a pull request run restores from its own ref
  and then the default branch. Delete the entry the hits actually come from,
  which the cache list shows with its ref.
- Entries not accessed for about a week are removed, so per-job keys on
  rarely run jobs come back cold.
- A cache fix can change what a gate executes, not just how fast; compare
  executed work. A warm cache can let a tool replay earlier results instead of
  running them, so the faster gate does less.

## Verify

```sh
muda compare --before 2026-09-01..2026-09-08 --after 2026-09-08..2026-09-15 --gates
muda record check
```

The dates above are example windows; replace them with representative before/after windows.
The first run after the fix saves a full-size entry, visible in the save line and
in the repository's cache list. Later runs on the same key restore it, and the
setup or build step is faster for identical work. Repeat the check after the
next key change: the full job again saves first. Each required check executes
the same work as before: compare tests run, packages built and steps run in
the logs, not only the time. Verify on the real PR pipeline
and again after merge. The gate inventory must remain the same or stronger; the
user confirms the receipt.

## Evidence

Illustrative example only, not a measured adopter result: a shared dependency
entry of a few hundred kilobytes is hit on every run while the install step
takes 6 minutes; after the light jobs stop saving and the entry is repopulated,
a several-hundred-megabyte entry is restored and the same step takes 1 minute.
In a Go variant, the required test step also looks faster after the fix, but
most test packages print `(cached)`: the warm build cache let `go test` replay
results instead of running them, while the gate inventory reads unchanged.
`-count=1` restores a full run, and the receipt times that run.
Record actual before/after measurements, coverage, cache sizes, keys and
run/job/step sources in the finding receipt; never substitute these example numbers.
