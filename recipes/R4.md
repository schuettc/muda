## Symptom

Image A rebuilds when only sibling image B changes, because both hash the whole
source tree to reach a shared lock.

## Detect

```sh
muda measure
muda logs 12345
```

Run ID 12345 is illustrative; substitute the measured run ID and inspect all
relevant jobs, including separate image-build jobs. Missing logs are unavailable
evidence, not zero work.
Read each context, Dockerfile, target and exclusion list. Change only one sibling
and compare staged contexts, identities and image-job outcomes by asset. The
agent diagnoses W1; empty deploy logs do not prove image reuse.
Compare each merged diff with the Dockerfile's COPY set: an image rebuilt when
the diff touched no COPY source most likely has a stray file in its context;
confirm it with the fingerprint oracle under Verify.

## Fix

Give each asset a minimal, explicit context containing everything it consumes
and none of its sibling-only inputs. Keep genuinely shared inputs in both. Test
staged contexts and hash sensitivity. Approve the scope with the user, then PR.
Guard the context in both directions: every file left in it is a COPY source,
the Dockerfile or `.dockerignore`, and every COPY source and the Dockerfile are
present. For new repositories, build contexts from an allowlist.

## Stacks

### cdk

Before: both `DockerImageAsset` definitions use the repository root without
exclusions. After: each excludes the sibling’s package directories while
retaining shared locks and source. Test the real staged contexts and expected
asset identities, including Dockerfile and target. The guard computes the
context exactly as the asset does: the context's `.dockerignore` plus the
asset's exclude, plus `!.dockerignore` and `!<Dockerfile basename>`, in DOCKER
ignore mode over `git ls-files` (with a large output buffer), using CDK's own
ignore strategy.

### docker

Before: `COPY . .` includes every package. After: scoped `COPY` instructions
and context-specific exclusions retain exactly their inputs. If a shared
`.dockerignore` would exclude files another image needs, use per-Dockerfile
ignore files or separately staged contexts. An allowlist context is a root
`.dockerignore` of `*`, then `!<needed paths>`, then pruned tests, scripts and
caches inside them; that shape cannot accumulate strays.

## Traps

- Two workloads with the same Dockerfile, target and context may be one
  deduplicated asset despite different runtime commands. Count assets, not consumers.
- Tests must assert both required files and sibling exclusion; over-exclusion
  can produce a fast but broken build.
- Shared lock changes legitimately affect both images. Validate all readers
  and writers of any generated lock artifact, including release jobs.
- Guards that only prove excludes never drop a COPY'd file miss the reverse.
  Common strays: CI-only locks and version files, the sibling image's inputs,
  files the release bump edits, a root test config, and a changelog kept by
  un-excluding `*.md` to retain a README. Each release then rebuilds the image
  and redeploys its consumers with no image change.
- Both ignore modes accept `!` re-includes, but only DOCKER mode can re-include
  a file inside an excluded directory; GLOB mode skips an excluded directory
  whole, and matches bare patterns against any path segment.
- A per-image list must also exclude the sibling's Dockerfile, locks and
  entrypoint.
- Shrinking a context moves the hash once, so the first deploy rolls once, by
  design.
- Correct a diagnosis if later hash evidence disproves it (lesson 6); do not
  silently replace the old receipt.

## Verify

```sh
muda compare --before 2026-09-01..2026-09-08 --after 2026-09-08..2026-09-15 --gates
muda record check
```

The dates above are example windows; replace them with representative before/after windows.
A sibling-only edit changes only the intended asset; shared-input edits change
all affected assets. Take the asset fingerprint before and after touching each
former stray: it must not move. Touching a real source file must move it.
Build and smoke-test every unique staged context with complete build/push/skip
evidence and unchanged gates.
Verify on the real PR pipeline and again after merge. The gate inventory must
remain the same or stronger; the user confirms the receipt.

## Evidence

Illustrative example only, not a measured adopter result: a sibling-only edit previously rebuilt 2 distinct assets; now it rebuilds
only the 1 affected asset, and releases that touch no COPY source go from 1
image rebuild to 0.
Record actual before/after measurements, coverage, tree/asset identities and
run/job/step sources in the finding receipt; never substitute these example numbers.
