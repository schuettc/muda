title: Deploy contracts first, then every stack at once

## Symptom

A consumer stack deploys only after its producers have finished their whole
deploy (image builds, service rollouts), although all it reads from them are a
few parameter values that never change: queue names, URLs, job-definition
names. The deploy's critical path is the producers' deploy plus the
consumer's.

## Detect

```sh
muda measure
muda logs 12345 --job 67890 --grep "(?i)UPDATE_IN_PROGRESS|UPDATE_COMPLETE|deploying"
```

Run ID 12345 and job ID 67890 are illustrative; substitute the measured deploy
job. Then, in the infrastructure code:

1. List every cross-stack read: parameter-store reads, `Fn::ImportValue`
   (which also makes the producer's export undeletable and unchangeable while
   imported), and stack dependencies.
2. Classify each value: a contract is a stable name derived from config; a
   derived value is an ARN with a revision, a digest or a generated ID.
3. In the deploy log, find consumers that start only after producers finish,
   where every value they read is a contract.

Ask the user for the parameters' history (when each was last written) if the
logs cannot show it; contracts are written once and rarely change.

## Fix

A contracts stack writes every contract value from config, and owns any
resource a contract names. It deploys first, as its own workflow step; every
other stack then deploys at the same time. Anything a contract names exists
when that step finishes, so every deploy is correct in one run. Approve one
scoped finding and change per PR.

Adding a contract takes one release. Renaming one takes two: expand (write the
new value beside the old one), then contract (remove the old one once nothing
reads it).

## Stacks

### cdk

Before: consumers read producer-written parameters, and either a stack
dependency or the workflow's step order makes them wait for the producers.
After: a contracts stack writes the parameters from the same config the
producers name their resources from; no stack depends on another, and the
ordering is the workflow's step order alone. Pin it with tests: no stack reads
a parameter that a stack in the same or a later concurrent step writes, except
through the contracts stack; contract values equal the producers' resource
names from one config source; no stack dependencies.

A consumer that uses `Fn::ImportValue` is still bound to its producer after the
ordering is removed: CloudFormation refuses to change or delete an export while
any stack imports it. Move the consumer to the contracts stack's parameter
first, deploy it, and only then remove the export from the producer (CDK's
`exportValue` can keep an export alive for that one release).

### github-actions

Before: one deploy step, or several in a line, deploys producers then
consumers. After: a contracts step, then one step (or parallel jobs) that
deploys every other stack concurrently, bounded by the runner.

## Traps

- Derived values are never contracts; a consumer that reads one still waits.
- Stateful resources such as queues cannot move to the contracts stack except
  by retaining and importing them.
- A conditional consumer must be decided by config, not by whether another
  step succeeded in the same run.
- Concurrency is bounded by the runner's size.
- The old producer-written parameters stay deployed after the move (lingering
  expand, a candidate waste in the standard). Record them as a finding with a
  removal date and a tracking issue in the same change, and remove them once
  nothing reads them.
- That a fresh environment comes up in one run follows from the design but has
  not been measured; test it before relying on it.

## Verify

```sh
muda compare --before 2026-09-01..2026-09-08 --after 2026-09-08..2026-09-15 --gates
muda record check
```

The dates above are example windows; replace them with representative
before/after windows. In the post-merge deploy logs, the consumer's rollout
overlaps its producers' instead of following them. The contracts stack's values
equal the parameters the producers used to write. Verify on the real PR
pipeline and again after merge. The gate inventory must remain the same or
stronger; the user confirms the receipt.

## Evidence

From one adopter's deploys on a 4-CPU, 16 GB runner: a consumer that waited
13.3 minutes for its producers, then took 245 seconds to roll out, now rolls
out alongside them (both about 3m24s, overlapping) on 2 of 2 deploys, saving
about 4 minutes of the critical path. All 7 contract values matched the old
producer-written parameters byte for byte. Record actual before/after
measurements and their run/job/step sources in the finding receipt; never
substitute these numbers.
